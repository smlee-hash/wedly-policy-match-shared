## 1. 풀려는 문제

ERP 와 일루아가 같은 화면·같은 판정 규칙을 **각자의 사본**으로 들고 있다. 실측(2026-09-04):

| 사실 | 값 |
|---|---|
| 일루아의 판정 핵심 5파일 | ERP 커밋 `18f3f5529`(2026-08-30)와 **바이트 동일** — ERP 가 9/3~9/4 에 4번 고친 것이 하나도 안 넘어옴 |
| ERP 자금 조달 지도 의존 폐쇄 | 56파일 11,003줄 |
| 일루아에 없는 것 | 36파일(자금 지도 전부) |

사본을 하나 더 만들면 「ERP 를 고치면 일루아는 자동으로 바뀌나?」의 답이 영원히 **아니오**다. 이 패키지는 그 답을 **예**로 바꾸기 위해 만든다 — 두 앱이 **같은 커밋을 물면** 코드가 글자 단위로 같아진다.

## 2. 무엇을 넣고 무엇을 안 넣나 (경계 규칙 하나)

**규칙: 패키지 안에는 「어느 앱인지」를 묻는 코드가 한 줄도 없다.** 앱마다 다른 것은 전부 **인자로 받는다**. `if (app === "erp")` 같은 분기가 생기면 그건 경계를 잘못 그은 것이다.

| 층 | 내용 | 왜 여기 |
|---|---|---|
| `src/engine/` | `structure-types` · `match-engine` · `recommend-score` · `region-augment` · `rule-extract` · `wedly-category` · `types` · `profile-summary` | 순수 판정 — 입력이 같으면 출력이 같다. 두 앱이 다를 이유가 없다 |
| `src/funding/` | `funding-group` · `funding-map`(낱말 도우미·필터·정렬·집계) · `amount-rate-extract` · `products/{types,rules-to-conditions,sources/manual}` | 순수 규칙 |
| `src/build/` | `buildFundingMap(profile, now, opts, loaders)` | 계산은 같고 **자료를 어디서 읽는지만** 다르다 → 읽기를 인자로 |
| `src/ui/` | `FundingMap` · `FundingDrawer` · `FundingRecommendPanel` · `Badge` · `SidePanel` · `CustomSelect`(+`selectGrouping`·`selectKeyboard`) | 화면 — 두 앱이 같은 모양이어야 한다 |
| **패키지 밖(앱 몫)** | Prisma 클라이언트·자료 읽기 구현 · 통로(route) · 인증·회사 접근 검사 · 회사 프로필 조립(`profile-loader`·`customer-360`) · 스키마 | 앱마다 **정말로** 다르다. ERP 는 로그인 세션, 일루아는 파트너 회사 범위 검사 |

### 2-a. 자료 읽기 인자 (`FundingMapLoaders`)

지금 `buildFundingMap` 은 `prisma` 를 직접 부른다. 이것만 걷어낸다.

```ts
export interface FundingMapLoaders {
  loadAnnouncements(now: Date): Promise<AnnouncementRow[]>;  // 19칸
  loadProducts(): Promise<FinanceProductRow[]>;              // 16칸
}
export async function buildFundingMap(
  profile: BusinessProfile, now: Date, opts: BuildFundingMapOptions, loaders: FundingMapLoaders,
): Promise<FundingMapResult>;
```

행 **모양(타입)** 은 패키지가 정하고, **읽는 방법**은 앱이 낸다. ERP 는 기존 `open-announcements.ts`(캐시 포함)를 그대로 loader 로 넘기고, 일루아는 같은 select 를 하는 얇은 loader 를 새로 쓴다. 두 앱의 Prisma 모델 칸 이름이 같으므로(같은 DB) loader 구현은 사실상 같지만, **타입 검사는 각 앱의 Prisma 클라이언트로** 받는다.

### 2-b. 화면 인자 (`FundingRecommendPanel`)

상세창 탭 본체는 다음만 앱에서 받는다. 나머지(상태·재조회·오류 표시·빈 상태)는 패키지 안.

| props | ERP | 일루아 |
|---|---|---|
| `endpoint` | `/api/policy-match/funding-map` | 같음 |
| `query` | `{ bizno, name }` | `{ bizno }` (상호 폴백 금지 — 유출 구멍) |
| `parseError` | `json.error.message` | `errMsg(json, …)` (문자열 규약) |
| `refreshEventName` | `COMPANY_STATUS_SAVED_EVENT` | 같음(파일이 양쪽에 동일) |
| `onOpenDetail` | 상세 바꿔치기 | 같음 |

### 2-c. 바탕 부품 — `@wedly/ui-shared` 는 **peer dependency**

`EmptyState·SegmentedControl·Skeleton·StatCard·StatusBox·Table` 과 `cn` 은 `@wedly/ui-shared` 에서 가져온다. **두 앱의 ui-shared 핀이 갈라져 있어도 안전하다** — 2026-09-04 실측으로 이 7개는 두 핀에서 **코드가 글자 단위로 동일**(다른 것은 주석뿐)임을 확인했다. 그래서 **ui-shared 포크 정리는 이 작업의 선행 조건이 아니다.**
`Badge·SidePanel·CustomSelect` 는 ui-shared 에 **없고** ERP 에만 있으므로 이 패키지가 가져간다.

## 3. 앱이 바뀌는 방식 — 「같은 자리에 한 줄 껍데기」

기존 소비자 파일을 한 줄도 고치지 않는다. ERP 소비자 수 실측: `match-engine` 13 · `types` 14 · `structure-types` 10 · `Badge` 27 · `CustomSelect` 44 · `cn` 99.

```ts
// ERP src/lib/policy-match/match-engine.ts (구현을 지우고 껍데기만)
export * from "@wedly/policy-match-shared/match-engine";
```

기본 내보내기가 있는 것(`FundingMap`·`FundingDrawer`·`CustomSelect`)은 `export { default } from …; export * from …;` 로. 이건 ERP 가 이미 쓰는 관례다(`src/components/ui/Table.tsx` 7줄 껍데기).

## 4. 「자동 반영」을 실제로 보장하는 장치 3개

패키지만으로는 부족하다 — 앱이 서로 다른 커밋을 물면 도로 갈라진다. 그래서:

1. **갈래는 `main` 하나.** 앱별 갈래(`-erp`/`-illua`)를 만들지 않는다(그게 `ui-shared` 를 3중 포크로 만든 원인). 앱별 정책은 **인자**로 푼다.
2. **핀 어긋남 관문** `~/.claude/hooks/shared-pin-guard.sh` — 두 앱 `package.json` 의 `@wedly/policy-match-shared` 핀이 다르면 답변을 끝낼 수 없다. 사장님 방식대로 「메모리 말고 훅으로」.
3. **패키지 CI**(GitHub Actions) — 밀 때마다 전체 시험. 앱 빌드 관문은 `node_modules` 를 제외해서 패키지 시험을 못 돌리므로([[erp-gate-cannot-run-shared-package-tests]]), 앱마다 **얇은 계약 시험** 하나를 두어 핀을 올리다 판정이 뒤집히면 배포가 막히게 한다.

## 5. 옮기는 시험

패키지가 순수 층을 가져가므로 그 시험(약 5,000줄)도 함께 간다: `funding-map`(1,040) · `funding-map-build`(1,011) · `funding-map-render`(1,211) · `funding-drawer-render`(364) · `amount-rate-extract`(264) · `funding-group`(116) · `rules-to-conditions`(91) · `match-engine`·`structure-types`·`recommend-score`·`region-augment`·`rule-extract`·`types`·`wedly-category`·`profile-summary`.
앱에는 계약 시험만 남긴다(ERP·일루아 각 1파일): 패키지에서 불러온 함수로 ① 갈래 분류 ② 마감 낱말 ③ 필터 기본값(안 맞음 제외) ④ 화면이 「D-」·「맞는 것만」 낱말을 안 쓰는지 ⑤ 통로 응답 모양.

## 6. 하지 않는 것

- `@wedly/ui-shared`·`@wedly/detail-modal-shared` 포크 통합 — 이 작업의 조건이 아님(§2-c). 별건.
- 정책매칭 화면 본체(`/policy-match`)를 일루아에 만들기 — 상세창 탭만(사장님 결정).
- 수집기·AI 구조화·슬랙 알림을 일루아에 두기 — 9/2 결정 유지. 공고 자료는 공유 DB 에서 읽는다.
- 하이브 반영 — 사장님 결정으로 제외(패키지가 생겼으니 나중에 핀만 물리면 된다).

## 7. 위험과 대비

| 위험 | 대비 |
|---|---|
| 새 git 부품이 Railway 에서 설치 실패(ssh 권한) | 저장소를 **공개**로 만들었고, 두 서비스 모두 `GIT_CONFIG_*` https 재작성 변수가 이미 있음(2026-09-04 실측) |
| 껍데기 재수출이 기본 내보내기를 안 넘김 | 기본 내보내기 4곳은 `export { default }` 를 함께 적고 tsc 로 확인 |
| Tailwind 가 패키지 안 클래스를 못 뽑음 | 패키지가 `src/styles.css` 에 `@source "./**/*.{ts,tsx}"` 를 스스로 등록하고 두 앱 `globals.css` 가 `@import` (일루아는 이미 `@wedly/*` 와일드카드 `@source` 가 있어 자동) |
| 패키지 시험이 앱 관문에서 안 돎 | §4-3 계약 시험 + CI |
| 일루아 스키마에 `FinanceProduct`·공고 5칸 없음 | 모델 정의만 추가(표·칸은 ERP 부팅 SQL 이 이미 운영 DB 에 반영) · `migrate`/`db push` 금지 |
| ERP 회귀(50+ 소비자) | 껍데기라 소비자 0줄 수정 · ERP `npm run build` 전량 통과가 관문 |
